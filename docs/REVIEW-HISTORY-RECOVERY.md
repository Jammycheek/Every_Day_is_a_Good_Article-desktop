# Re-review R1: confirmed revision-history recovery

Scope: synthetic public PoC under R2's exclusive recovery-directory ownership. A damaged/unreadable floor file, the 256-entry limit or an authoritative rollback with a reused incarnation could otherwise block PC editing indefinitely. Recovery now offers explicit identity-scoped forgetting and whole-file quarantine. Neither option proves the phone's state or automatically enables editing.

## Choices and caller confirmation
- Readable history: revisionHistoryEntries exposes at most 256 logical identity/incarnation/floor entries for a future selection UI. prepareForgetRevisionHistory(identity) returns that exact key and floor with an opaque one-use token; a missing key returns no preview. The selected entry alone is removed after affirmative confirmation. Other entries remain unchanged. Capacity never automatically evicts an entry; the user chooses one and is informed that it might still be relevant to a different dataset. No age ordering/retention duration is invented.
- Unreadable history: prepareQuarantineRevisionHistory returns a whole-history loss preview with unknown identity/count. Healthy readable history cannot take this path. After confirmation, the file is atomically renamed to a unique revision-floors-quarantine-UUID.dpapi file without decrypting, replacing or deleting it. Original bytes and ACL are retained. Startup never restores, promotes or removes archives automatically.
- Cancel calls cancelRevisionHistoryRecovery and changes no stored history. Tokens belong to one live journal preview; another preview, cancellation or close invalidates them. Confirmation consumes a token even on change/error. A changed file rejects recovery and requires another preview. No automatic retry occurs.

The future UI must show the key/floor for a scoped forget, or that all identities are unknown for quarantine; describe the loss of rollback protection; make cancel the default; and obtain a separate affirmative action. Suggested scoped notice: "このPCの確認済み版の履歴を忘れます。古い編集許可を見分ける防御が失われます。スマホ側の現在の状態を再確認してから再開します。保留編集は残ります。" Whole-file quarantine must additionally state that all prior history becomes unavailable. The token is not proof of human consent. There is no actual confirmation UI in this PoC.

recoverRevisionHistory always suspends the PC session, releases its snapshot and invalidates any pending-discard preview before invoking storage recovery, including an invalid maintenance request. It does not require MTP/a live editing grant. It never modifies pending.dpapi, phone data, authoritative operation state or session ownership on the phone. Pending incompatibility still blocks subsequent grants; use applied reconciliation or N4's separately confirmed local discard rather than silently clearing it.

## Persistent warning and restart behavior
Before changing history, storage atomically writes/forces an owner-only generic history-incomplete.warning file. It contains no identifiers or application content. Its presence is the conservative loss-warning bit; contents are intentionally not interpreted, so damage to its bytes cannot remove the warning or create a parsing/decryption dead end. The marker is retained permanently by this PoC, including after a new baseline and across restart. A warning alone can survive a failed recovery; this false positive is safer than silently losing the notice.

revisionHistoryIncomplete exposes the directory-wide warning. revisionHistoryNeedsBaseline(identity) is true when that warning exists and the current floor map lacks the specified key. After quarantine, every missing key needs its own explicit baseline. Restoring one key never unblocks another. After scoped forgetting, retained keys keep their floors and missing/new keys conservatively need explicit baseline. The actual UI must display the warning even after a key has been baselined; it must not imply the former history was recovered.

Ordinary acceptGrant rejects a key requiring a baseline. A future authenticated channel must first query current authoritative identity/incarnation/revision and operation state, issue a **new** request with replay protection, and then pass a verified fresh grant to acceptFreshHistoryBaseline. Reusing a cached grant is forbidden. That method checks transport, lease, retained floor and pending compatibility, persists the accepted base revision before returning permission, and verifies the new floor. No snapshot is restored automatically. A save failure suspends and leaves the missing key needing baseline. Once the validated floor is persisted, that key has a baseline even if the process stops before returning; future grants must still be freshly authenticated and cannot be below it.

This public API cannot itself prove freshness: Grant still has no authenticated request nonce/epoch/carrier. Naming the method or constructing its input is not authentication. Thus this is a caller-enforced synthetic boundary, not permission to enable real data. R1 does not excuse an authoritative app reusing an incarnation after restore; that private-side bug still must be fixed. Forgetting can intentionally allow a lower baseline and loses protection against older grants until correctly authenticated current state is established.

## Storage errors and consistency
Recovery holds the R2 owner lock throughout preview and mutation. If encrypted bytes can be read within the size limit, their exact contents are compared again before recovery. For oversized/raw-unreadable files, quarantine uses regular-file identity (when provided), size and last-modified attributes instead, without loading the payload. That weaker comparison relies on exclusive cooperating ownership and does not protect malicious/external same-metadata replacement. A changed/missing file returns CHANGED; inspection/read/move/write failures propagate with editing stopped. Non-regular files are rejected.

Warning creation precedes floor replacement or quarantine. Failure before mutation keeps the source untouched; later IO failures never report recovery success but may leave the old or atomically replaced/quarantined state and a marker. Inspect/re-preview under ownership before retrying; no automatic rollback is claimed. Quarantine success leaves no active floor file; it does not need old DPAPI keys to rename the file or record a generic warning. Establishing a new floor still needs working current-user DPAPI encryption. If Windows denies even file attribute inspection or rename, permissions/storage must be repaired before this API can proceed; it does not bypass OS access controls. Actual profile/key loss is not exercised by these tests.

This is ordinary atomic-file/process persistence, not a power-loss guarantee. Quarantine retention/export, secure erasure, authoritative status retention and capacity beyond confirmed removals need production policy. Deliberate deletion/restoration of history or the warning, old unlocked binaries and same-user attacks remain outside the protection. There is no automatic warning reset or archive cleanup.
