# Re-review N4: explicit local pending-edit discard

Scope: synthetic public PoC. A rejected, unknown or conflicting operation can remain pending at revision N while the phone advances to N+1. Its mismatched base blocks a new grant. The controller now offers an explicit local abandonment path for readable records, including unbound EAP1 records. Export, rebase and recovery of unreadable journals remain unimplemented.

## Caller flow and confirmation requirement
1. Authenticate and query the authoritative operation status where possible. A matching applied receipt uses reconcileApplied instead of discard. Pending/in-progress means wait/query; never treat local discard as cancellation of a phone transaction. Unknown status does not authorize retry.
2. If the user chooses to abandon the local pending edit, call preparePendingDiscard. It reads the protected record and returns application identity, incarnation (or unknown for legacy), base revision, operation ID, exact content digest and an opaque process-local confirmation token. It does not clear data, grant editing or interrupt an active session.
3. Show those details and the loss consequence in a future UI. Require a separate affirmative user action, with cancel as the default. Suggested notice: "PCに保留している編集を破棄します。復元できません。スマホで反映済みの変更は取り消せません。" For an unknown/in-progress remote outcome, explain that remote processing may still finish. Never automatically call discard on status failure, revision conflict, timeout or reconnect. cancelPendingDiscard invalidates that preview without touching storage.
4. Only after that action, pass the preview's token to discardPending. The controller reloads the record and checks exact metadata and digest. A token belongs to one controller and one preview, and can be used only once; preparing another preview, cancelling, staging or matching applied reconciliation invalidates it. A restart requires another preview/confirmation. A token is a capability, **not proof that a human confirmed**; the caller must enforce this UI requirement. No real confirmation UI exists in this PoC.
5. Successful discard suspends the session, releases its snapshot and removes only the local pending journal. It neither alters the phone nor clears the protected revision-floor history, creates a grant, restores a snapshot, resends or cancels an operation. Authenticate/query current state again and obtain an explicit fresh grant and snapshot before editing; the stored floor still rejects older grants. New edits must have fresh operation IDs in the production design.

## Results and failure behavior
R1 separately adds confirmed revision-floor recovery; see REVIEW-HISTORY-RECOVERY.md. Pending discard itself still never resets history. Unreadable pending-edit quarantine/export remains unimplemented.
| Result | Meaning | Session and storage |
| --- | --- | --- |
| DISCARDED | Preview matches the current readable record and deletion succeeded | Session suspended, snapshot released, pending removed, floors retained |
| NO_PENDING | Confirmed record is already absent | No deletion or session change; token consumed |
| INVALID_CONFIRMATION | No live matching preview, foreign/old/cancelled/reused token | No read, deletion or session change |
| CHANGED | Metadata or exact content changed since preview | Current pending and session unchanged; token consumed; new preview and confirmation required |
| Exception on read/delete | Storage/decryption/parse/delete failed | Editing suspended; failure propagates; no success reported; token consumed; no automatic retry or recovery-file removal |

Preparing an unreadable record fails, suspends editing and preserves its encrypted bytes. Readable unbound legacy records can be explicitly abandoned without assigning a guessed incarnation. Discard does not read, reset or rewrite the revision-floor file: even if that file is corrupt, future grants remain blocked by its read failure. R1 now supplies separately confirmed floor-history quarantine/rebaseline (see REVIEW-HISTORY-RECOVERY.md); unreadable pending records still need a separate quarantine/export design.

The only supported concurrency model remains one serialized controller/writer. WindowsDeltaJournal now holds exclusive directory ownership across the entire preview/confirmation interval; another cooperating journal cannot modify either protected file. See REVIEW-DIRECTORY-OWNERSHIP.md. In-process stage invalidates outstanding previews. Preview comparison alone is not a lock; external edits, old unlocked binaries, malicious same-user access and equal-content replacement/ABA outside the ownership protocol remain out of scope. File deletion is logical removal, not forensic secure erasure; protected remnants, backups and orphan temporary files follow the unresolved retention policy.

## Verification
Common tests simulate affirmative caller confirmation and check the changed-revision dead end, explicit later grant, floor retention/restart checks, no automatic editing, preview/cancel/foreign/forged/reused tokens, stale preview after payload/metadata change, no-pending no-op, applied-receipt invalidation, read/delete failures and readable legacy abandonment. Existing unrelated-receipt behavior remains covered.
Windows integration tests use actual DPAPI in newly created disposable directories. They verify that confirmed discard removes pending.dpapi while preserving the exact encrypted revision-floors.dpapi bytes, and that a reconstructed controller rejects an older grant and accepts an explicit current grant. A valid EAP1 fixture can be cancelled without modification and then explicitly discarded; a malformed legacy record cannot be previewed and its bytes remain intact.
